# HRX-OS AI研发团队治理制度

版本：1.0  
适用范围：GitHub仓库 `rongfei611-sys/-` 的 `hrx-recovery` 子项目，Recovery 0.7及后续增量。  
不适用：本地独立的 V19.6.10 交付包；本制度不声明该版本源码已同步到GitHub。

## 1. 组织与工具职责

- 首席架构师/GPT-6：负责总体架构、技术决策、业务逻辑、跨组协调、研发验收和风险升级。
- Superpowers：研发方法体系，执行需求澄清、方案比较、TDD、系统性调试、实施计划和代码审查流程。
- GitHub：代码资产、分支、PR、评审记录、CI运行和发布标签的唯一事实来源。
- 自动化测试：质量监督；只报告真实运行结果，不推测通过。
- 专业研发组：系统架构、前端、后端、数据、安全、测试、DevOps、业务专家。
- 统一质量验收与交付中心：独立核对证据、阻断不合格交付。

## 2. 任务生命周期

`INTAKE → DESIGN → READY → IMPLEMENT → REVIEW → VERIFY → ACCEPT → RELEASE`

每个任务必须记录：问题/业务价值、范围与非目标、责任组、业务Owner、风险、验收标准、依赖、回滚方式和证据链接。

## 3. 开发规则

1. 先阅读当前代码、迁移、API契约、AGENTS.md和已有测试。
2. 复杂需求先写设计说明和实施计划；用户已明确的技术选择不重复询问。
3. 先测试后实现；缺陷修复必须添加可复现回归测试。
4. 每个PR只包含一个可审查的主题，禁止把不相关的功能混在一起。
5. 代码必须通过格式/静态检查、单元测试、适用集成测试和安全检查。
6. 所有数据库变更采用新迁移；不得重写已发布迁移。
7. OIDC/权限/RLS默认拒绝；不得自动授权或绕过职责分离。
8. 外部系统、正式IdP、生产病毒库和生产数据没有真实连接时，必须明确标记BLOCKED/NOT CONFIGURED。
9. 任何人不得以CI通过代替业务Owner验收或生产环境验收。

## 4. PR与合并

- 通过Pull Request提交，不直接修改受保护分支。
- PR必须填写模板、关联任务、描述风险、附测试命令和结果。
- 必需CI：`HRX Recovery CI / Isolated verification`（首次运行后以GitHub显示的精确Check名称为准）。
- 高风险改动（认证、权限、RLS、迁移、文件服务、金额/库存/质量状态）必须由相应专业责任人审查。
- 评审意见必须逐项解决或说明不采纳原因。
- 未通过必需CI、存在未处理高危问题或缺少业务Owner验收，不得合并/发布。

## 5. 版本与发布

- 每个合并版本更新CHANGELOG/验证记录。
- 发布包包含源码、Manifest、SHA-256、变更清单、测试证据、部署/回滚说明。
- 生产门禁必须独立执行；环境阻塞不能被静态测试替代。
- 发布后保留可回滚标签和数据库备份恢复记录。

## 6. GitHub组织限制

当前仓库所有者是个人账号 `rongfei611-sys`，不是GitHub Organization。仓库目录中的专业组是工程责任分组，不等于GitHub Teams。当前可验证的仓库Owner为 `@rongfei611-sys`；未创建的团队和人员不写入CODEOWNERS。

GitHub Branch Protection读取请求返回403（Resource not accessible by integration），当前连接不具备分支保护管理API权限。因此本分支只提交保护策略与可执行管理员脚本，不声称规则已在GitHub服务器生效。管理员应用后须重新读取API/Settings并留存证据。
