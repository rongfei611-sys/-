# 研发工作流与交接标准

## 1. 任务入口

每项任务建立Issue或项目任务，至少填写：
- 业务问题、目标用户、预期价值
- 当前行为与期望行为
- 范围、非目标、依赖和风险
- 业务Owner、责任研发组
- 正常/异常/越权/并发/撤销场景
- 可观察、可复现的验收标准

## 2. 设计与拆分

复杂需求先形成设计说明和ADR，说明至少包含：现状、目标、方案比较、选择及代价、数据/API变化、安全边界、测试计划、回滚路径。拆分任务时标明输入、输出、负责人和交接条件。

## 3. TDD实施

1. 复现问题或编写失败测试。
2. 最小实现使测试通过。
3. 重构并运行相关回归。
4. 对数据库/权限改动增加真实隔离数据库测试。
5. 对关键用户旅程增加浏览器E2E。
6. 更新API契约、操作文档和缺失清单。

## 4. 分支与提交

- `feature/<issue>-<topic>`、`fix/<issue>-<topic>`、`governance/<topic>-YYYYMMDD`。
- 一个PR对应一个主要目标；提交信息使用动词和范围。
- 不提交.env、密钥、用户数据、临时文件、node_modules和构建缓存。
- 禁止force push；已发布迁移不得改写。

## 5. 评审交接

PR作者提供：改动摘要、影响模块、API/迁移、权限影响、测试命令/退出码、截图或日志、风险、部署和回滚步骤。评审人逐项检查正确性、安全性、可维护性和测试覆盖。

## 6. 验收状态

- PASS：测试在指定环境真实执行并通过。
- FAIL：实际测试失败。
- BLOCKED：缺少环境、权限、凭据或外部依赖。
- NOT RUN：尚未执行。
- ACCEPTED：业务Owner完成真实业务场景验收。

不允许把BLOCKED/NOT RUN转换成PASS。恢复工程的隔离测试不等于企业生产验收。
